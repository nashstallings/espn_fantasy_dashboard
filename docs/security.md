# Handling ESPN credentials

This app stores other people's live ESPN session cookies. That is the single
most sensitive thing it does, so the handling is written down here rather than
left implicit in the code.

## What is stored

| Value | Storage | Why |
| --- | --- | --- |
| `SWID` | Firestore, plaintext | ESPN's member id. It is the account key, and it does not authenticate anything on its own. |
| `espn_s2` | Firestore, AES-256-GCM ciphertext | The actual session secret. Encrypted with the SWID as additional authenticated data. |
| League list | Firestore, plaintext | League ids, names, and the user's team in each. |
| Session token | The user's browser (`localStorage`) | A JWT whose only claim is the SWID. No cookie material. |

Firestore documents are keyed by `sha256(SWID)`, so raw member ids are not
document names.

## Guarantees the tests enforce

- Invalid credentials are never persisted. `POST /api/connect` stores nothing
  until ESPN has accepted the cookies (`test_connect_rejects_cookies_espn_will_not_accept`).
- The stored blob never contains the plaintext cookie, and encrypting the same
  cookie twice produces different ciphertext (fresh nonce per encryption).
- A ciphertext cannot be replayed under a different SWID — the AAD binding fails
  authentication (`test_blob_cannot_be_replayed_under_another_swid`).
- No response echoes `espn_s2` (`test_connect_never_echoes_the_cookie`).
- Session tokens carry exactly `sub`, `iss`, `iat`, `exp` — nothing else.
  `alg: none` tokens and tokens signed with another secret are rejected.
- A session can only read leagues linked to its own account; a guessed league id
  returns 403 (`test_reading_a_league_you_have_not_linked_is_refused`).
- Response caching is keyed by SWID first, so one user's private league payload
  can never be served to another (`test_cache_is_keyed_per_user`).
- Disconnect deletes the stored record *and* flushes that user's cached
  payloads; a token issued before the disconnect stops working immediately.
- BigQuery snapshots contain league data only — no SWIDs, no cookies
  (`test_snapshot_carries_no_credential_material`).

## Key management

`CREDENTIAL_ENCRYPTION_KEY` is a 32-byte key in Secret Manager, injected into
Cloud Run at deploy time. It is generated by `infra/bootstrap.sh` and never
touches the repo.

`crypto.py` is the only module that sees ciphertext. Moving to Cloud KMS or
envelope encryption means rewriting `encrypt`/`decrypt` there and nothing else.

Rotating the key today invalidates every stored cookie — users would have to
reconnect. `CredentialRecord.version` exists as the hook for a dual-key
rotation if that becomes worth building.

## What a user can do

- **Disconnect** in the account dialog deletes everything the server holds for
  them, immediately.
- Logging out of ESPN invalidates `espn_s2` upstream, which makes the stored
  copy useless regardless of what this app does.

## Shared project

This app runs in `ff-python-api`, alongside Dynasty Tycoon, rather than in a
project of its own. That is a deliberate choice, and it is the one place where
the blast radius around stored ESPN cookies is wider than it has to be: anything
with broad project-level IAM there — an owner/editor role, or a service account
granted `roles/datastore.user` for another workload — can read the credential
documents, even though nothing in Dynasty Tycoon has a reason to.

What keeps that bounded:

- The dashboard's own service account (`espn-dashboard-api`) is created fresh by
  `bootstrap.sh` and granted only `datastore.user`, `bigquery.dataEditor`, and
  `bigquery.jobUser`.
- Credentials live in their own Firestore collection (`espn_credentials`), and
  the BigQuery snapshots go to their own dataset (`espn_fantasy`) — no shared
  tables with the Dynasty datasets.
- `espn_s2` is encrypted regardless, and the key lives in Secret Manager with
  access granted only to this service account. Project-level Firestore read
  access alone yields ciphertext, not cookies.

Moving to a dedicated project later means re-running `bootstrap.sh` with a
different `PROJECT` and re-connecting accounts; nothing in the code assumes the
project it sits in.

## Known limits

- A session token stays valid for its full TTL (default 30 days). There is no
  server-side revocation list; disconnecting deletes the credential record,
  which is what actually makes the token useless.
- `localStorage` is readable by any script on the origin. The token grants
  read-only access to the user's own leagues and cannot be used against ESPN
  directly, but the site must never load third-party scripts.
- Cloud Run is deployed `--allow-unauthenticated` because the browser calls it
  directly; authorization is the bearer token, and CORS is pinned to the Pages
  origin.
